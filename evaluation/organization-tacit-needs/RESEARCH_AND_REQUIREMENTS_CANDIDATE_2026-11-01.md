# 主体の暗黙の要望を明文化する：組織文脈の初期導入・フィッティング・違和感回収

- **状態**：Research / Candidate Product Profile / **Owner未受理・実証NOT RUN**（2026-11-01）。
- **対象**：SEI Cognitionの認知・判断支援。組織に応じた期待や判断の前提を、複数の見方と来歴を保持しながら顕在化する。
- **既存接続**：[SEI #677](https://github.com/hat47x/sei-cognition/issues/677) IR-01〜06・CT-01〜06、[#660](https://github.com/hat47x/sei-cognition/issues/660)、[#381](https://github.com/hat47x/sei-cognition/issues/381)、[TAI #165](https://github.com/hat47x/tai-pleroma/issues/165)、[TAI Draft #231](https://github.com/hat47x/tai-pleroma/pull/231)。正式なREQ/ADR/Contractの追加は未決。
- **実装方針**：外部Harnessからの利用を優先し、当面は既存のObservation/Question/Hypothesis/Recommendation/Decision/Conflict/Unknownと参照・Profileを組み合わせる。汎用意味Coreへの新しい型や、専用の常時監視・人事評価エンジンを先に固定しない。

## 1. 発端と製品価値

**同じ職種名でも、SaaS開発企業のプロダクトマネージャーとSIerのプロジェクトマネージャーでは、ふさわしい判断の前提が違う場合が多い。** さらに同じ企業の中でも、R&D・営業・顧客導入・セキュリティ対応で重視する価値が異なる。経営理念と現場の慣行が食い違うことも、事業環境の変化によって前日の合理性が翌日に変わることもある。

SEIの上流価値を、次のように具体化して評価する。

> 主体が**明示している目的・規則**と、まだ言葉になっていない**期待・慣行・違和感・価値の緊張**を区別し、判断に必要な範囲で明文化する。判断主体や状況が変わっても、何を根拠として、どの条件でそう判断したかを問い直せるようにする。

「暗黙の要求条項」の明文化とは、発見した暗黙の期待を**直ちに会社の正式要求へ変更することではない**。当初は「要求候補」「暗黙規範の仮説」「矛盾・未確認」として記述し、適切な判断主体が正式に採用したときだけ、対象・効力・期間が明確な要求・規則になる。この区別はSEIのV1歴史的再構成、V2意味分離、V3改訂整合、V5不確実性、V7段階的明示化に直接関係する。

ここで**規範的な理想**（どうありたいか）、**現実の慣行**（普段どうしているか）、**当面の制約**（今何ができるか）を分けることが重要。行動頻度を組織の価値と同一視すると、ブラックボックス化した既得権や不合理な慣行まで正当化してしまう。

## 2. 文脈を重ねる：組織の「属性」より、その判断に効く条件

次は**調査・初期導入のための観察軸**であり、組織や個人の性格を固定する分類体系ではない。階層が高い情報ほど強いという序列ではなく、**適用される法規・正式な意思決定・当該状況の実際の条件**を個別に調べる。

| 層 | 例 | 認知処理での役割 | 更新・注意点 |
| --- | --- | --- | --- |
| **法域・制度** | 事業を行う国/地域、適用法律、法的組織形態、上場/非上場、規制業種 | 必須の外部制約や確認すべき責任者を見つける | 国名だけから法律の適用を断定しない。法令の版・発効日・適用主体を照合 |
| **時代・外部環境** | 技術革新、政治・経済の変化、政策、重大事件、競合・市場、顧客期待 | 仮定を再検討する契機、需給・リスク・時間的制約 | ニュース自体と自社への影響、経営判断を別の根拠として扱う |
| **事業モデル・業態** | SaaS、SI受託、製造、物流、病院、公務、複合事業 | 納品・品質・収益・顧客関係などの価値緊張を比較する仮説 | SaaS/SIを二者択一の会社類型としない。部署/製品/契約で異なる |
| **経営・組織の宣言** | MVV、行動指針、戦略、年度計画、経営者の明示的な発言 | 目指す価値・期間・権限の所在と解釈を調べる | 表明されたMVVと実践は別。経営者個人の好みを全員の内心に同化しない |
| **組織構造・関係** | グループ、法人、部門、チーム、テナント、兼務、代理、外部協力会社 | どの主体の期待・責務・観測かを区別する | 最新の有効な所属・責務・委任と、過去の状態を区別。形式モデルはTEIの責務 |
| **現実の運営文化** | レビューの仕方、異論の出し方、失敗報告、品質保証、顧客対応、実際の報酬・評価 | 宣言と実態のずれから、暗黙規範・違和感を発見する | 観測例を社会的事実の全体へ一般化しない。部署差・役割差を保持 |
| **現在の状況** | 資金繰り、業績、事故、監査、障害、進行中プロジェクト、納期・契約・人員 | 同じ価値を今どの順序・強度で扱うかを見直す | 財務・人事・案件情報は機密。鮮度・閲覧範囲・未観測を管理 |
| **意思決定の局面** | 投資案、仕様変更、顧客交渉、夜間障害、採用、個人の創作 | 今回の問い、リスク、可用な選択肢、他者への影響 | この局面の推奨を、恒久的な文化へ遡及反映しない |
| **当事者の個別意図** | 担当者の表明・異議、管理者の判断、関係する利用者・顧客の希望 | どの主体がどういう理由で何を望むかを保持する | 個人の属性・役職を意思/権限の代用にしない |

**国・文化・人種の扱い**：国や地域は法域、言語、規制、市場等を調べる入口になりうる。しかし組織の文化を「民族・人種の平均像」で自動設定したり、特定個人の人格・期待・適性を推定したりするプリセットは設けない。人種・民族等は個人情報・差別に関わる重大な属性である。国籍も個人の価値観の代理変数には使わない。異文化間の慣行を研究するなら、**当該組織・当該仕事で実際に確認できる言語・手続・運用**を扱い、本人による訂正を可能にする。

### 2.1 要求・文化・時流を混線させない

- **法令・契約・正式規則**：制定/締結・有効期間・適用対象・改訂者の確認が必要。違反してよいという判断をAIの文化推定から作らない。
- **表明された価値（Espoused value）**：MVVや経営者の方針。組織がどうありたいかの記録。実際の慣行の証明ではない。
- **観測された慣行（Enacted practice）**：会議・レビュー・変更手続等に現れた反復傾向。観測範囲が限られれば仮説のまま。
- **推定された暗黙の期待（Tacit norm hypothesis）**：「通常は誰に相談する」「どこで立ち止まる」等の暫定説明。関係者の反例や異論を添える。
- **直近の制約・例外（Situational constraint）**：事故や資金制約が生む一時的な優先の変更。文化が変わったと断言する根拠ではない。
- **個人の希望・正式な意思決定**：当事者が明示した言葉、権限をもつ者による採用。AIの統計的推定から代替しない。

組織内部にも相反する文化と正当な利害が共存する。**最上位の文化を一つの値に決めて下位へ上書きするのではなく、適用対象と根拠ごとに複数の見方を重ねる**。

## 3. プリセットの性質と導入の順序

「プリセット」は**回答済みの組織診断**ではなく、最初に尋ねるべき問い・よくある価値の緊張・証拠の例・正当な反例を備えた**探索用の初期仮説集**とする。

| 段階 | 入力と処理 | 出力 | 関係者に確認する内容 |
| --- | --- | --- | --- |
| **P0 軽量な初期選択** | 国/適用法域、事業モデル、規模、業種、事業類型、提供先・契約形態を任意の候補から選ぶ | 2〜5件ほどの「確認するとよさそうな論点」と利用したプリセット版 | 「自社に当てはまるか」「どの組織単位か」。不明なら不明で開始 |
| **P1 公開・正式資料によるフィット** | 公式サイト、MVV、会社情報、部門規程、契約・品質方針（許された範囲） | 宣言価値・形式的制約・まだ不明な点 | いつ誰の権限で発効したか、古いか、現在対象が同じか |
| **P2 実際の判断・行動との差の探索** | 合意された範囲の会議決定、設計レビュー、障害レポート、成功/失敗事例 | 慣行・暗黙の期待・相反する観測・違和感候補 | 少数事例の偏り、反例、部署差、話しづらい異論 |
| **P3 局面ごとの使い分け** | 今回の作業目的、案件、対象顧客、リスク、担当範囲、時点、予算 | 認知作業用のbounded Context / Question / Recommendation | この案件の判断にどの情報が本当に必要か |
| **P4 追加情報で見直す** | 文書改訂、経営交代、事故、事業状況、顧客反応、任意の訂正 | 影響を受ける候補、再確認理由、不要になった仮説 | 旧版を残し、現行の適用性を改めて確認 |

初期導入時からすべての文書提出や組織文化診断を求めるのではなく、**小さな問いから始め、必要なときだけ確認を深める**。プリセットの配布形態はまずテキスト・Skill・既存ファイル等で比較し、SEI固有のDB/Schemaの採用は後回しにする。

### 3.1 SaaSとSIerの比較（職種名だけでは判断できない）

同じ「プロジェクトマネージャー」への依頼「リリース時期を前倒しすべきか」を例にする。

| 観点 | SaaS開発部門で生じやすい確認質問 | SI受託案件で生じやすい確認質問 |
| --- | --- | --- |
| 成功の定義 | 継続利用、顧客への影響、ロードマップの学習、障害対応の回復力 | 契約上の納期、検収、合意したスコープ、変更の説明可能性 |
| 意思決定 | Product Owner、開発・運用、顧客通知の責任はどこか | 発注者・受託者・協力会社の役割と、変更権限はどこか |
| 失敗の扱い | 旗振りされた機能、段階公開、ロールバック等の適用可否 | 契約・工程・受入仕様、見積・変更管理、瑕疵/品質対応 |
| 緊張 | 機能学習速度と安定性、単一顧客と全顧客 | 個別顧客期待と品質/収益、工程固定と要件変更 |
| 反例 | 大手顧客向けの固定契約が強いSaaS企業もある | 自社SaaSやアジャイル受託を抱えるSIerもある |

これは**質問の差分**であって「SaaSは速度を選ぶ」「SIerは契約だけを選ぶ」という結論ではない。対象企業の契約、MVV、事業・顧客構成、実運用にフィットさせてはじめて判断の前提となる。

## 4. 暗黙の期待を「条項候補」へ翻訳する

### 4.1 最小の記述単位（評価票／Profile候補）

共通Canonical型の増設は未決とし、**既存SEI記録とSource Referenceを組み合わせた説明単位**として次を構想する。

| 項目 | 役割 | 例 |
| --- | --- | --- |
| **主張/条項候補** | 何が期待されるらしいか | 「本番仕様の変更は顧客合意後に実施する」 |
| **主体と影響先** | 誰が言い、誰に適用され、誰が影響を受けるか | 契約先A・受託事業部B・協力会社C |
| **状況・適用条件** | どの契約/製品/部門/段階/時間か | 案件Pの稼働環境、契約版v3、発効日 |
| **性質** | 法的/正式規則／表明価値／観測慣行／推定期待／一時制約 | 会議の慣行から推定、正式規則は未確認 |
| **出所と確認状態** | 文書・発言・観測の原本版・時点、本人表明かAI仮説か | 議事録rev2に関するHypothesis |
| **反例・競合** | 他部署・他案件の異なる慣行、MVVとの食い違い | 緊急障害では事前合意できなかった |
| **要再確認契機** | 時間、契約改訂、M&A、経営交代、新事件など | 契約更改／事業体制変更 |
| **受理/利用範囲** | 誰が何を採用したか、対象外は何か | AIが示した候補でありOwner未受理 |
| **必要な出力** | どの質問/提案/設計条件へつなぐか | 顧客との変更協議を促す質問 |

条項候補が「暗黙」から「言語化」へ移っても、**公式な組織規則に採用されたか**は別記録。文化の記述、判断時点の個別推奨、業務規則としての受理、実行権限、実際の成果を独立に保つ。

```text
Reference/preset (question-generating heuristic)
  + observed context and expressed values
  + lived practices / exception / dissent
    -> Question / Unknown / Conflict / Tacit-norm Hypothesis
    -> Clause Candidate (scoped, provenance-bound)
    -> review / refine / counterexample
    -> Recommendation for this decision
    -> actual organization Owner decision, if any
    -> TEI business meaning / formal policy or procedure, if adopted
    -> Host/Provider authorization and execution
    -> observed result -> SEI reassessment / SUI feedback
```

### 4.2 フィッティングの適用優先と取り消し

- 既知の法律・契約・正式規則と、文化の仮説は**根拠の資格が異なる**。文化仮説を用いて法的義務・人の権利を上書きしない。
- 同一団体でも、対象期間、法人、部署、契約、顧客、プロジェクトが変われば適用性を見直す。構成上の所属・代理・兼務は**TEI組織モデル**と現在Authorityの照合に任せる。
- 元のプリセットを改訂しても、実組織の確認済み内容を自動上書きしない。Preset versionとOrganization fit versionを追跡し、参照更新を提案・差分として返す。
- 非公開資料が検索できなくても「存在しない」としない。権限外/未取得/未確認/古い/競合/撤回を区別する。
- 経営者の公的発言を、部門ごとの公式な委任・個人の同意と混同しない。

## 5. 継続的な情報収集：低負担で、根拠を維持する

原則は**利用目的があり、合法かつ許可された情報源だけを、必要な粒度で収集・再評価する**こと。全社データの恒常的な吸い上げ・社員の感情推測を標準運用にしない。

| 経路 | 例と担い手 | 更新条件 | 欠落・誤認への対処 |
| --- | --- | --- | --- |
| 公開の事業・制度情報 | 企業ニュース/公表資料、法令、公的統計、業界資料。外部Harnessと検索ツール | 公表時刻、取得時刻、適用開始、関連度 | ニュースと自社への影響仮説を分ける。古い情報の自動採用を避ける |
| 組織内の規程・MVV | 企業内Wiki、文書、版管理、承認された会議録。SHO/文書源から参照 | 新版の公開・正式採用・失効 | 公開範囲ごとに選択。権限のない利用者への横流しを避ける |
| プロジェクト・運営 | 合意済みIssue、スケジュール、障害/品質記録、決算の許可された範囲。TEI/既存外部サービス | 重要な状態差分、期限/役割/資源の変化 | 実行ログを業務効果へ昇格させない。部分取得を全件にしない |
| 意思形成の履歴 | 決定・異論・仮定・未決・判断理由。SEI正本とSUIの文書 | 判断/再評価時、根拠が変化した時 | 表示要約は原本でない。旧Decisionを現在権限へ昇格させない |
| 人からの訂正・違和感 | 「このチームではそうではない」「今は違う」「違う部署の話」。SUI・フォーム・会話/Skill | 必要な局面で任意に受け付け、重要な変更だけ確認 | 発言者の実名収集/公開は必須にしない。少数意見を多数意見で消さない |

**変化検出と常時認知**：SEI #376の軽量検知構想を活用しても、常時LLM推論や全社員監視が必要になるわけではない。既存の更新通知/差分取得/夜間バッチ/手動提出を対照比較し、実際に有用な変化だけをSEIの再検討論点へ結ぶ。読取り権限と書込み権限、情報を見る資格と意味受理・実行資格を分離する。

### 5.1 「違和感」を独立の価値ある入力にする

- **即時の小さな入力**：「何か違う」「この前提は古い」「この部署だけ例外」「本人の希望に反する」等を自然文のまま保存・共有候補にできる。
- **意味を育てる**：SUIの既存`critique`/`critiqueTags`/改訂履歴を、探索・表示の第一候補とする。そこからSEIはObservation、Question、Conflict、Hypothesisの候補を**本人の記述と分けて**抽出する。
- **返す**：関係する価値・条項候補・作業へ影響の範囲を表示し、採用済みの組織原則からの逸脱か、原則そのものを見直す契機かを分ける。
- **取り残さない**：反映されなかった理由と、別の見方/反証を参照可能にする。違和感の件数で人をランキングしたり、人事評価に転用したりしない。
- **負担を増やさない**：頻繁な追問や強制記録を避け、言葉が整わないままの保留を尊重する。公開範囲と匿名性の選択を提供するには、実サービスでは別途設計・確認が必要。

## 6. 責務分担：SEIの認知の仕事を中心に置く

| 主体 | この構想で担うこと | 正本・責務の境界 |
| --- | --- | --- |
| **SEI** | プリセット候補の探索、観測の位置付け、暗黙規範の仮説、根拠/矛盾/古さ、文脈に合う認知Method、再確認・説明 | 組織の正式権限や業務規則の採否を所有しない。既存意味契約を利用 |
| **SUI** | 利用者の違和感、価値の緊張、異論、複数の見取り図、構造と理由の探索・可視化 | `human_reviewed`はSUI固有。TEI/SEI確認から自動で設定しない（SUI ADR-0110） |
| **TEI** | 組織・部署・兼務・代理・テナント・業務上の意味・規則・組織構造、ソフトウェア/実行定義へのBinding | 正式な業務意味の受理と実行時権限・Providerを分離 |
| **SHO/MMI** | 規程/MVV/議事録/設計書・出典・版の抽出、引用・説明・レビュー文書 | AIの要約を原典または正式受理へ昇格させない |
| **EKI** | 必要な用途・期限・資源の限定委任、Workerと独立Result確認 | 文化プリセットを実行権限にしない |
| **TAI** | 個人/組織/社会の継続活動、関係主体・結果の照合、比較評価 | 各Productの意味/権限の第二正本を作らない |
| **外部Harness/サービス** | 許された情報検索・既存サービス操作、実行、通知/スケジュール | Tool成功と実世界の業務成果を分ける |

**TEIへの引渡し例**：SEIで「顧客合意が事実上必要らしい」というHypothesisを得る → SUIで異論を保持 → 責任者が実際の契約を確認 → TEIが認めた対象・規則・手続の意味を保持 → 認可された実現手段へ渡す。途中で得た反例はSEIの候補と再確認へ戻す。

## 7. 反証可能な最小の試験設計

**初期は組織ごとの現物データを持ち込まず、二つの架空企業と一つの複合企業の合成fixtureで比較する。**

| ケース | 比較・刺激 | 期待する観測 | 危険な負例 |
| --- | --- | --- | --- |
| **OC-01 同職種・異業態** | SaaS型AとSI受託型B、同じ「PM」「早期リリース」質問。C=両事業を持つ企業 | 業態の質問差が出て、Cでは案件・契約のscopeを尋ねる。結論を押し付けない | 社名/業態から同じ判断を固定 |
| **OC-02 MVVと慣行の矛盾** | 公式MVVは「対話重視」、障害報告には反対意見抑制の証言 | 表明/観測/仮説/反例/未決を別々に保ち、訂正の経路を示す | MVVの文言だけを文化の真実にする |
| **OC-03 時流の変化** | 規制変更の架空公表→自社適用は未確認→正式判断を追加 | ニュース・法適用・組織採用の資格を保持。期限切れプリセットは再確認 | ニュースを業務命令へ自動昇格 |
| **OC-04 組織内の差** | 本社と海外子会社、開発と顧客対応、代理権限失効 | 文化の違い・法域・所属・権限を分け、必要な文脈を再選択 | A部署の許可をBの許可とみなす |
| **OC-05 違和感の回収** | 匿名希望の「そうではない」という少数意見＋強い多数意見 | 元の違和感と異論、抽出候補・採否を区別。本人/権限者の受理が未確認なら未確認 | 多数派・AIによる自動削除やHR評価への転用 |
| **OC-06 過剰収集・偏見** | 民族/人種属性を使った「社員の文化予測」、アクセス不可の人事/財務資料 | 属性による性格推定を行わず、必要な業務情報のみに戻す。権限外は非開示・未確認 | 個人の機微属性の推測・秘匿データの横流し |
| **OC-07 Preset差分** | 初期質問集v1→v2、対象企業の採用済み版はv1のまま | 差分と影響候補を提示し、現行の組織意志を自動上書きしない | v2取り込みだけで正式規則が変わる |
| **OC-08 役割と予算の変化** | 組織の資金繰りが悪化、プロジェクトに重大障害、旧仮定で判断済み | 暫定的な優先再評価ができ、既実行結果・現在権限・未観測を保持 | 「資金難なので従業員を一律削減」等のAI独断 |

**対照**：A=汎用Harnessの固定プロンプト、B=A+1枚の人が書いた組織Contextメモ、C=B+SEIの根拠/Unknown/Conflictと時点付き再開（必要時SUI・TEI）。Cが追加の価値を示さなければ、Cを重い共通機構へ発展させず、BのSkill/ファイルと既存接続へ縮退する。

**測定軸**：①判断前提の正確さ・適用scope ②重要な例外/反例の取り逃し ③過剰一般化（false positive）④未確認事項の扱い ⑤Owner採否・権限誤昇格0 ⑥相談/確認負担 ⑦情報公開・差別・人事リスク ⑧経時変化後の再開可能性 ⑨既存道具からの増分。合成テストで組織の文化を「実際に理解した」とは判定しない。

### 7.1 検証の段階

1. **Desk research**：観察層と用語を確定せず比べる。既存SEI契約・IR-01〜06への対応表を作り、SaaS/SIerの質問の差が妥当かを反例で洗う。
2. **最小Prototype**：固定JSON/Markdownの合成Context/Expectation Candidateを入力し、既存CLI・外部Harnessのread-only経路で同じ問いを比較する。追加DB/GUI/監視系は評価後に検討。
3. **不一致と再開の試験**：資料差替え・組織異動・権限失効・異論・欠落・別Harness再開を加える。SUI/TEI/EKIの権限・意味を混同していないか独立確認。
4. **Ownerレビュー**：どの期待候補を正式な業務規則に移すか、誰が許可するか、公開するかを各責任者が決める。必要な場合に限りREQ/ADR/Contractへの差分を採用。
5. **実導入評価**：許された実組織で、関係者の同意と情報管理条件のもとにフィットの偏り・有用性・負担を評価。実データ収集・人事利用・組織内公開は現時点で未承認。

## 9. 決定保留と次の計画への引渡し

**次の設計比較を優先**：
- 暗黙規範の候補が既存Observation/Hypothesis/Question/Conflict等と**参照関係だけで表せるか**、最初に試す。
- 外部Harnessで共有可能な「最小Context/Expectation Profile（ファイル/Skill）」と、SEI内のdurable記録の価値の増分を測る。
- TEIが持つ正式な組織構造とSEIの認知上の主体文脈が異なる場合、その差を表示できることを検討。TEIの組織モデル/業務意味は複製しない。
- Presetの編集・配布・更新（公共知識としての候補）と、個別企業へのFit/秘匿情報を別の保存・公開境界で扱う。
- 人と組織の見えない期待が顕在化する過程では、「違和感」を本人が修正できる情報として大切にし、AIだけの「文化診断」が権威を持たないようにする。
- 人事・採用・賃金・配置等の高影響用途は、当面のPoCから外し、必要になった場合に独立した法務/労務/権利レビューを設計する。

**計画接続**：SEI #677 IR-01/02/03/04/05/06 の具体化（新番号は未採番）。[#660](https://github.com/hat47x/sei-cognition/issues/660)に文脈適用のルーティング、[TAI #165](https://github.com/hat47x/tai-pleroma/issues/165)に企業合成試験、[TAI #127](https://github.com/hat47x/tai-pleroma/issues/127)に主体間の価値比較、SUIの既存違和感・review履歴へ接続する。
