# SOZA Product Value

更新日: 2026-08-31  
状態: **Product Value Baseline**

## 1. SOZAが存在する理由

綜座（SOZA）は、人間・AI・組織・プロジェクトなどの主体が、**何を観察し、何をまだ分かっていないと認め、何を問い、何を根拠として、どのように判断したか**を失わずに扱うための認知・意思決定基盤です。

SOZAの価値は、処理を大量に自動化すること自体にはありません。AIや実行基盤が高度化し、現在のワークフローやエージェント実装が置き換わっても残る、判断の意味・根拠・不確実性・責任・来歴を保つことにあります。

この文書は「SOZAがなぜ存在するか」と「何を価値として守るか」を定めます。価値同士が衝突したときの優先関係、Universal Coreへ含める基準、Product Valueを満たしたと判断するための検証観点は`SOZA_VALUE_MODEL.md`で、実際にどのEvidenceをもって満たしたと判断するかは`SOZA_VALUE_ACCEPTANCE.md`で具体化します。

## 2. 解こうとする問題

高度なAIや多数の外部システムを利用すると、処理は速くなっても、次のものが失われやすくなります。

- 何が事実として観察され、何が推測だったのか。
- 何が分からないまま残っていたのか。
- 相反する情報がどこに存在したのか。
- 提案と最終判断を誰がどのように区別したのか。
- どのCapabilityを、どの条件と根拠で選んだのか。
- 判断時点では何を知っており、その後何が変わったのか。
- 実行結果が、判断や前提をどのように更新したのか。

SOZAは、これらを実行ランタイムの内部状態や一時的なプロンプトへ閉じ込めず、後から人間とAIの双方が読み直せる形で保持します。

## 3. 提供する中核価値

### 3.1 不確実性を消さずに前へ進める

SOZAは、`Unknown`をNoへ、`Conflict`を最新値へ、`Hypothesis`を事実へ自動的に潰しません。

分からないことや対立した証拠を残したままでも、必要な判断を行い、その判断がどの不確実性を抱えていたかを後から再構成できることを価値とします。

### 3.2 提案・判断・権限・実行を分ける

SOZAでは、少なくとも次を同一視しません。

```text
Recommendation != Decision != Authority != Action Intent != Execution
```

AIが強い提案を出せることと、それを採用する判断、実行権限、実際の実行は別です。この分離により、自動化を進めても責任線と統制可能性を失いにくくします。

### 3.3 判断の記憶を残す

SOZAは、最終結果だけでなく、**その時点で何を根拠に判断したか**を残します。

後から前提・観察・Capability・制約が変わっても、過去の判断を書き換えて現在の知識へ合わせるのではなく、当時の判断を当時の状態として復元できることを重視します。

### 3.4 CapabilityとProviderを分け、手段を交換可能にする

SOZAは「何を可能にするか」と「誰／何がそれを実現するか」を分けます。

人間、AI、SaaS、外部組織、TEI、custom codeなどを、必要に応じて異質なCapability Providerとして扱います。SOZA自身と関係の深い技術であることだけを理由に、特定Providerを優遇しません。

これにより、利用技術が置き換わっても、Intent・Constraint・Decision・Provenance等の意味を保ちやすくします。

### 3.5 実行基盤より上位の意味を保持する

workflow、BPM、agent runtime、queue、retry、worker scheduling等は重要ですが、それらをSOZAの恒久的な中心にはしません。

SOZAは、外部の実行基盤をCapability Providerとして利用できる一方、それらが置き換わっても残る認知・判断の意味構造を所有します。

### 3.6 人間とAIが同じ判断面を読めるようにする

SOZAの記録は、機械処理可能であるだけでなく、人間が意味を追える必要があります。

過剰な内部推論やprivate chain-of-thoughtの保存ではなく、観察、問い、根拠、未解決点、判断理由、責任、来歴など、外在化して共有すべき情報を扱います。

## 4. 価値を測るときの考え方

SOZAの価値を、単純な自動化率や実行件数だけで評価しません。

重要なのは、たとえば次の問いに答えられることです。

1. 判断時点の根拠と未解決点を後から再構成できるか。
2. AIの提案と、人間・組織のDecisionを区別できるか。
3. Providerを交換しても、IntentやDecisionの意味が壊れないか。
4. 相反するEvidenceやUnknownを保持したまま扱えるか。
5. 過去のDecisionを現在の知識で上書きせず、変更の来歴を辿れるか。
6. 実行ランタイムが変わっても、SOZAの中核価値が残るか。

これらを実際の設計評価へ使うときは、`SOZA_VALUE_MODEL.md`のV1〜V8へ展開します。単一の総合点へ還元せず、どの価値を満たし、どこに未充足やtrade-offが残るかを個別に確認します。

さらに、「満たしている」という主張の高さを正確にするため、`SOZA_VALUE_ACCEPTANCE.md`ではDesign、Executable、Release、Operational Evidenceを分けます。設計文書が整っているだけでactual repositoryやproductionで実証済みとは扱いません。

## 5. SOZAが価値としないもの

SOZAは、次をそれ自体の目的とはしません。

- ワークフロー実行量の最大化
- agent turn数や自律実行率の最大化
- 特定AIモデルへの最適化
- 特定Providerへの囲い込み
- Universalな単一スコアによる判断の自動化
- すべての仕事をSOZA内部で実行すること
- 実装量やコード量を製品価値とみなすこと

## 6. 長期的に守る中心

技術が進歩するほど、現在の実装・プロンプト・オーケストレーションの一部は不要になります。

SOZAが守るべき中心は、それらの仕組みではなく、**認識、問い、不確実性、根拠、判断、責任、Capability、来歴を、人間とAIが後から読み直し、選び直せる状態に保つこと**です。
