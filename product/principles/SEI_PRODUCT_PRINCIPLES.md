# SEIの製品設計原則

更新日: 2026-10-10  
状態: **製品設計原則の基準版。ブランド世界から得た知見を反映済み。** §18の正当化の札と縮小の条件は、ADR-0035（Proposed）による提案であり、採否は未決です。この提案は基準版の規範に含めず、採否が決まるまで提案として扱います。

## 1. この文書の役割

本書は、`SEI_PRODUCT_VALUE.md`と`SEI_VALUE_MODEL.md`で定めた価値を、マイルストーン、要求、ADR、全体構成、実装へ具体化する際に、繰り返し適用する設計原則をまとめたものです。

個別の型やAPIを直接決める文書ではありません。下位設計で迷ったときに、どちらの方向がSEIの製品価値に合うかを判断するために使います。

## 2. 意味を実装より先に置く

SEIでは、現在のコード、データベース、指示文、業務の流れ、AIエージェントの実行環境を、製品の恒久的な中核とはみなしません。

まず守るべき意味の違いを定め、その後で実現手段を選びます。実装が便利だからという理由だけで意味構造を決めません。

## 3. 観測・解釈・提案・判断を混ぜない

SEIでは、観察したこと、そこから読み取ったこと、採用を提案した案、実際に採用した判断（Decision）を、必要な範囲で区別します。

```text
Observation
  != Interpretation / Hypothesis
  != Recommendation
  != Decision
```

常にすべてを別々の成果物（Artifact）へ分割することまでは求めません。重要なのは、後から意味の違いを復元できることです。

## 4. 不確実性を正直に保持する

未確定事項（`Unknown`）、対立（`Conflict`）、仮説（`Hypothesis`）、観察の不足を、都合よく確定した値に変えません。

判断が必要な場合は、不確実性を残したままでも判断でき、その時点で何が未解決だったかを後から辿れる構造を優先します。

`not observed`を`unavailable`や`false`へ暗黙変換しません。

## 5. 早く結論を出しすぎず、必要な判断は避けない

AIや組織が一つの説明を流暢に生成できることを、十分に検討された結論と同一視しません。

十分な根拠のない観察、別の解釈、対立、未確定事項、仮説が残っている場合は、それらを必要な期間保持し、何が未解決かを読み取れる状態を優先します。

一方、結論を出さないこと自体を価値とみなして、必要な判断を無期限に先送りすることもしません。期限、影響、責任、権限などから判断が必要であれば、未解決を消さずにDecisionへ進みます。

```text
not forcing premature closure
  != refusing necessary decisions
```

## 6. 提案・判断・権限・実行を分ける

```text
Recommendation != Decision != Authority != Action Intent != Execution
```

提案が優れていること、採用判断が行われたこと、権限があること、実行されたことは別の意味です。

AIの能力向上や自動化率の上昇を理由に、この境界を暗黙化しません。

## 7. 情報の来歴と意味の変遷を残す

どこから得た情報か、どの経路で発見したか、何をもとに派生したか、どの意味変更が何を置き換えたかを区別します。

保存データの改訂番号、Gitのコミット、データベースの版などを、意味上の識別子や意味の改訂番号と同一視しません。

## 8. 過去を現在の知識で上書きしない

現在の理解が変わっても、過去の判断が、その当時どの根拠、観察、未確定事項、制約などを参照していたかを再構成できるようにします。

最新状態だけを残して履歴を消す設計を避けます。

## 9. 能力とその提供元を分ける

能力（Capability）は「何ができるか」、提供元（Provider）は「誰が、または何がその能力を提供するか」を示します。

```text
Capability != Provider
```

人間、AI、SaaS、外部組織、TEI、個別に実装したコードなどを、その種類だけを理由に信頼、優先度、権限と結び付けません。

## 10. 提供元を交換できるようにする

SEIの意味構造は、特定のAIモデル、SaaS、業務の流れを実行する仕組み、BPM、TEI、データベースなどを交換しても保てることを目指します。

提供元に固有の情報が必要な場合は、汎用の中核へ組み込む前に、提供元または用途別の設定へ分けられないか検討します。

提供元を変更した結果、意図、判断、責任の意味まで変わる設計を避けます。

## 11. 中核を小さく保ちつつ、必要な意味の区別を残す

中核を小さくすること自体は目的ではありません。

一方、現在の実装の都合だけで、汎用の型を増やしすぎることも避けます。Coreへ追加する概念は、現在の具体Scenarioで必要であり、技術が大幅に進歩しても区別する意味が残ることを確認します。

既存概念の組み合わせ、参照例、拡張、用途別の設定、能力の提供元、専門分野の知識によって十分に表せる場合は、新しい汎用型を追加しないことを優先します。

## 12. 表示を簡略化しても意味の正本は保つ

利用者にすべての意味境界を常時見せる必要はありません。

画面や入力を簡略化する場合も、重要な意味を知らないうちに消さず、必要なときには正本の意味へ戻れる構造を優先します。

```text
Simple View != Lossy Canonical Model
```

読みやすさや操作性のために意味を省略する場合は、表示上の省略と意味上の削除を区別します。

## 13. 必要に応じて意味の明示度を高める

すべての作業へ同じ重い記録手続きを要求しません。

影響が小さく取り消せる作業と、影響が大きい、取り消せない、不確実性や外部への影響が大きい作業とでは、明示すべき意味の範囲が異なって構いません。

ただし、AI自身が申告する確信度だけを理由に、重要な意味の区別を省略しません。必要な明示性はProfile / Policy等として外在化します。

## 14. 利用者の注意力を不必要に奪わない

AIが大量の提案を生成できること、常に通知できること、詳しい情報を何でも表示できることは、それだけでは製品価値とみなしません。

利用者の注意力には限りがあります。SEIによる介入、通知、提案、詳細情報の表示は、利用者にとっての利益、緊急性、重要性、利用者が制御できることによって正当化できる程度にとどめます。

```text
more assistance
  != better assistance

quiet
  != passive
  != hiding material change
```

安全上の重要な兆候、重大な対立、再検討が必要になる条件などを、静けさを理由に隠してはなりません。通常時の低い認知pressureと、必要時の適切なproactive assistanceを両立させます。

## 15. 認知成果の共有と利用権限の境界を同時に考える

認知の成果を一人の利用者、一つのAIとの対話、一つの提供元の一時的な状態へ閉じ込めないことを重視します。同時に、共有可能であることを無制限公開や共同Authorityと同一視しません。

```text
shared cognition
  != unrestricted disclosure
  != shared Decision Authority
```

別の主体がcanonical meaningへ戻れる設計では、Selective Disclosure、Product Access、Responsibility、Authority、Provenance、context egressを同時に考えます。

利用権限の境界が必要だからという理由で認知の成果を対話ごとに分断せず、共有価値を理由に必要な境界を取り払わないことを原則とします。

## 16. 評価時点から10〜50倍程度先を見る

将来耐性は、固定された「100倍未来」の想定ではなく、評価時点の現実からおおむね10〜50倍程度先を見渡す移動基準として扱います。

この倍率は性能の評価基準ではありません。現在の制約への過適合を見つけるための思考上の距離です。

主要なArchitecture Rebaselineや技術環境の変化に応じて、新しい現在地から設計候補を再評価します。

## 17. 実装順序と世界の意味構造を混同しない

M48、M49等のhistorical Milestoneは開発上の順序です。

実装の順番を、そのまま利用者世界の必須workflowやontologyへ変換しません。Product Milestoneも同様に、製品成立の確認点であってUniversal ontologyではありません。

## 18. 不要になったコードや指示文を手放す

より優れたAIや標準技術が現れ、SEI内部のコードや指示文が不要になった場合は、無理に維持しません。

削れる実装は削り、意味契約と検証可能な境界を残します。

### 提案: 正当化の札と縮小の条件（ADR-0035 / ISSUE-000088、Proposed）

この小節は基準本文ではなく、ADR-0035（Proposed）による提案です。採否が決まるまで、基準としては扱いません。ADR-0035を支えるのはDesign Evidenceだけであり、その評価も生成AIによるもので、製品の所有者によるレビューはまだ受けていません。

提案では、何を削れるかを場当たりに決めないため、各仕組みに、なぜ必要なのかを示す札を付けることとします。札は次の三種類です。三分類の名称はADR-0035 Decision 6によります。ただし、札を付ける目的と以下の各分類の由来の説明は本書の補足であり、ADR-0035の本文ではありません。

- **制度**: 提案では、権限、責任、時間、複数の主体に由来する仕組みとし、モデルが強くなっても残る、あるいは強まると想定します。
- **容量**: 提案では、モデルの弱さを補うために必要な仕組みとし、モデルが強くなるにつれて薄くなる可能性が高いとします。
- **経済物理**: 提案では、コスト、電力、通信、プライバシーに由来する仕組みとし、一部は残ると想定します。

新しい世代の基盤モデルが出たときの再評価は、ADR-0001（評価時点から動く将来基準でCore候補を見直す）の考え方を実際に動かすきっかけとして扱い、その記録では`historical PASS != current PASS`を守ることとします。

札ごとの縮小の条件（何が観測されたら縮小または再設計するか）は、ADR-0035の定めに従い、`plan/issue/ISSUE-000088-maintain-model-progress-robustness-register.md`の台帳で維持します。この台帳の一般化は、`evaluation/cognitive-workspace-comparison/README.md` §2.1に提案として示されています。同節は未採用の提案であり、確立した先例ではありません。

本節は、ADR-0035の再検討条件（Revisit conditions）のうち、本節の提案に関係するものを抜粋します。次のいずれかが観測されたときは、該当する仕組みを再検討します。

- 新しい世代の基盤モデルでの再評価で、制度に由来するとした仕組みまで薄くなることが観測された。
- ベンダーの記憶機能や利用者所有の記憶の標準が、判断の根拠、来歴、提案と決定と権限の区別まで運ぶようになり、SEIとの差が縮んだ。

## 19. 人間が理解できることを設計品質とする

SEIの重要な文書や成果物は、機械が処理できるだけでなく、人間が読んで意味を確認できることを重視します。

開発文書については、内容と構造を作成した後に、意味や仕様を変えず、**自然な日本語となることを最重要視して全文をドラフトし直す工程**を必ず設けます。

新規文書だけでなく、既存のactiveな開発文書もすべてこの工程を通します。historical evidence等、原文保存が必要な資料は本文を改変せず、除外理由と日本語の案内を別途残します。

## 20. 確認した根拠を超えて成果を主張しない

ローカルの試験用データ、人工的な試験、設計の点検、本番環境の運用を区別します。

設計が整ったことを実装済みと呼ばず、ローカル試験のPASSを運用実績と呼ばず、実際に確認できたEvidenceを超えてcoverageやrelease状態を引き上げません。

```text
Execution Success != Decision Validity
Method Application != Assurance
```

実行に成功したことやMethodを適用したことだけから、判断や結論が正しかったと主張しません。

## 21. 製品価値を一つの点数にまとめない

SEIの価値を、一つの総合点や汎用の評価点にまとめません。

`SEI_VALUE_MODEL.md`のV1〜V8をはじめとする複数の観点から、何を満たし、どこにtrade-offや未充足が残るかを個別に確認します。

一つの評価軸で優れていることを理由に、別の重大な価値欠損を相殺したことにはしません。

## 22. 関連製品だからといって優遇しない

TEIやSUIを含む関連製品・技術を、SEIとの関係が近いという理由で自動的に優先しません。

同じIntent、Constraint、Evidence、Decision境界のもとで、他のCognitive Method / Capability Providerと比較可能であることを原則とします。

ブランド上の象徴的な親和性を、必須依存、固定pipeline、Provider優先の理由にしません。

## 23. 仮説・実証・要求を分ける

製品として何を要求すべきか十分に分かっていない領域を、早い段階で確定した要求として固定しません。

```text
Open Question
  → Discussion / Research / Experiment
  → Candidate Requirement
  → Stable Requirement
```

チャット上の議論、資料調査、prototype、fixture、human review等は、Requirementを発見・反証するための入力として利用します。ただし、それらの途中結論を自動的にcurrent Requirementへ昇格させません。

stable Requirementへ進める前に、Product Valueとの関係、具体Scenario、既存REQとの重複、配置層、将来耐性、観測可能なAcceptanceを確認します。

調査の結果、既存Requirementで十分である、または新しいRequirementは不要であるという結論も正当です。

ブランド世界や比喩も同様です。象徴的な整合性だけからRequirementやUniversal ontologyを演繹しません。

## 24. 製品価値の変更には明示的な見直しを求める

下位実装の都合だけでProduct ValueやValue Modelを書き換えません。

上位価値を変更する必要が生じた場合は、反証Evidence、影響範囲、互換性、Revisit条件を明示し、通常の実装変更とは分けて再基線化します。

Product Valueの変更後は、影響するMilestone、Requirements、ADR、Architecture、Implementationを上位から再監査します。
