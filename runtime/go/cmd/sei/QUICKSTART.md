# sei クイックスタート

更新日: 2026-10-06  
状態: **Experimental / v1alpha1。導入容易性は未観測(ISSUE-000084のE-84.1)**

`sei`は、AIツールや人の提案と、人が下した決定を、別の記録として残し、後から続きを始められるようにするコマンドです。単一のバイナリで動き、外部のDBやサービスは要りません。

## 1. 入手する

配布用のバイナリがある場合は、お使いの環境のファイルを取得し、`SHA256SUMS`と照合してください。

自分でビルドする場合は、Go 1.25以上で次を実行します。

```bash
sh tools/build_sei.sh ./dist
```

指定したディレクトリ(上の例では`./dist`)に、Linux、macOS、Windows向けのバイナリと`SHA256SUMS`ができます。ディレクトリがなければ作られます。

## 2. 最初の判断を記録する

作業するディレクトリで、次を順に実行します。記録は、そのディレクトリの`.sei/`に保存されます。

```bash
sei init
sei add recommendation --id R-vendor-a --statement "ベンダーAを選ぶ" --source tool-a
sei add recommendation --id R-vendor-b --statement "ベンダーBを選ぶ" --source tool-b
sei add decision --id D-vendor --statement "ベンダーAを1年間採用する" \
  --recommendation R-vendor-a \
  --unresolved question:exit-cost \
  --responsible person:team-lead
```

ここで記録した内容は、次の意味に分かれています。

- 推薦(recommendation)は、提案です。決定ではありません。
- 決定(decision)は、依拠した推薦、未解決のまま残した問い、責任を持つ人を持てます。

## 3. 続きを始める

数日後でも、別のAIや別の担当者でも、次で現在地に戻れます。

```bash
sei resume
```

決定、未解決の問い、まだ誰も依拠していない推薦が分かれて表示されます。機械から読むときは`--json`を付けます。

## 4. 第三者が検証する

```bash
sei export --output decisions.json
sei verify --input decisions.json
```

`verify`は、`.sei/`も`sei`の記録も持たない環境で動きます。ファイルだけで、形式の検証ができます。

## 5. 実行の前に確認する

AIツールやスクリプトが何かを実行する前に、その根拠となる決定が方針を満たしているかを確認できます。

```bash
sei gate check --decision D-vendor
```

終了コードは次の三つです。呼び出し側は、0以外をすべて「進まない」と扱うと、確認できなかった場合に安全側へ倒れます。

| 終了コード | 意味 |
|---|---|
| 0 | 許可。記録された決定が方針を満たしている |
| 3 | 拒否。理由が出力される |
| 1 | 確認できなかった(storeがない、storeが不正、引数の誤りなど) |

既定の方針は「決定が責任を持つ人を名指ししていること」です。`--require-recommendation`で依拠した推薦を、`--deny-unresolved`で未解決が残っていないことを、追加で求められます。

許可は、責任を持つ人が実際にその権限を持つことの確認ではなく、行為が決定の範囲に収まっていることの確認でもありません。出力の`not_verified`に、確認していない事項が出ます。確認自体は何も実行せず、判断の記録(`semantic.bundle.json`)も変更しません。

確認のたびに、時刻、結果、方針が`gate-checks.jsonl`に追記されます。このログは運用のための記録で、`sei export`の書き出しには含まれません。ログに書けない場合は、許可を出さずに終了コード1で失敗します。

## 6. AIツールから使う

MCP(Model Context Protocol)に対応するAIツールには、次のコマンドをMCP serverとして登録します。通信は標準入出力です。

```bash
sei mcp --data-root /path/to/.sei
```

AIツールが自分の作業ディレクトリで`sei`を起動する想定です。この環境では確認していません。そのため、`sei`のパスも`--data-root`も、相対パスではなく絶対パスで指定してください。

### Claude Codeへの登録

次のコマンドで登録できる想定です。ただし、この環境では実行して確かめていません。お使いのClaude Codeのバージョンで`claude mcp add`の構文が合っているかを確認してから使ってください。パスはお使いの環境のものに置き換えてください。

```bash
claude mcp add sei -- /absolute/path/to/sei mcp --data-root /absolute/path/to/.sei
```

登録は、お使いのClaude Codeの設定を変更します。チームで共有したい場合は、リポジトリの`.mcp.json`に次のように書く方法もあります。

```json
{
  "mcpServers": {
    "sei": {
      "command": "/absolute/path/to/sei",
      "args": ["mcp", "--data-root", "/absolute/path/to/.sei"]
    }
  }
}
```

`.mcp.json`の書式も、この環境では読み込ませて確かめていません。お使いのClaude Codeのバージョンの書式と合っているかを確認してください。

登録した後は、Claude Codeを新しく起動し直してください。ただし、再起動で登録が反映されることは、この環境では確認していません。

### 動作の確認

事前に、`sei init --data-root /absolute/path/to/.sei`で記録の置き場を作っておきます。そのうえで、AIツールに次のように頼んでみてください。以下は試すための手順で、この環境ではまだ通していません。

1. 「seiのresumeを見せて」と頼む。現在地が表示されれば、読み取りが通ったと判断できます。
2. 「ベンダーAを選ぶ推薦を、id R-1で記録して」と頼む。記録後に、ターミナルで`sei resume --data-root /absolute/path/to/.sei`を実行し、推薦が出所つきで現れれば、追記が通ったと判断できます。
3. 「seiに決定を記録して」と頼む。既定では、`add_decision`が存在しないため、記録できないと答えるのが正しい動作です。
4. 存在しない決定IDで「check_decisionで確認して」と頼む。`deny`が判定結果として返れば、確認が通ったと判断できます。

3で決定が記録されてしまった場合は、既定の制限が働いていません。そのまま報告してください。

AIツールに渡る操作は、既定では次の三つだけです。

- `resume` — 現在地を読む。
- `add_recommendation` — 推薦を追記する。決定にはならない。
- `check_decision` — 実行の前に、決定が方針を満たすかを確認する。拒否は、失敗ではなく判定結果として返る。

AIツールが決定を記録できるようにするには、運用者が`--allow-decision`を付けて起動します。そのときも、責任を持つ人(`responsible`)を一人以上指定しないと記録できません。空の値を渡した場合、方針のフラグに真偽値以外を渡した場合、認識できない引数を渡した場合は、無視されず、エラーとして拒否されます。

`sei mcp`経由で書かれた記録には、AIツールがMCPの初期化(initialize)で名乗ったクライアント名が出所として残ります。呼び出し側がこの名前を別のものに選ぶことはできません。コマンドラインから書いた記録が出所として持つのは、`--source`で指定された値だけです。指定しなければ、出所は残りません。

`--allow-decision`を付けた運用で成立することと、成立しないことは次のとおりです。

- 成立すること: 決定の記録には、責任者(`responsible`)が必ず付きます。出所には、クライアントが名乗った名前が残ります。名前が空なら`mcp-client`が入ります。
- 成立しないこと: クライアント名は自己申告で、認証されていません。クライアントは任意の名前を名乗れるため、記録の出所から人とAIとツールを区別することはできません。出所の種別(`kind`)は常に`source`で、`resume`が出すのはIDだけです。
- 成立しないこと: `responsible`は任意の`kind:id`で、そのIDが実在の人や役割を指すこと、その人が内容を確認したことは検査されません。`sei check`は、責任者がAuthorityを持つことを未確認として出します。
- 以上から、MCP経由で記録された決定は、人が決めたという根拠になりません。人が確認したことを示すには、運用者が別の手段で確かめてください。本人確認、署名、確認手順はSEIの契約にまだなく、設ける場合は別途の設計判断になります。

## 7. 守られていること

- 追記のみです。記録済みの内容は書き換えられず、同じIDの追加は失敗します。
- 認識できない形式の記録は、削除されず、そのまま残り、未検証として表示されます。
- 未解決は、決定が残したまま、未解決として表示されます。
- 同じstoreに対する同時のコマンドは、`store.lock`というロックファイルで直列化されます。クラッシュしたプロセスがロックを残した場合、コマンドはその旨を表示します。`sei`のプロセスが動いていないことを確かめてから、利用者が`store.lock`を手で削除してください。
- `add decision --recommendation`に指定できるのは、storeに記録済みの推薦だけです。
- `export`は、既に存在するファイルを上書きしません。

## 8. まだできないこと

- 確認の結果は、運用のログ(`gate-checks.jsonl`)に残るだけで、判断の記録の一部ではありません。確認は実行も止めません。実行を止めるかどうかは、呼び出し側が終了コードで決めます。
- 同じstoreへの同時のコマンドは`store.lock`で直列化されますが、複数の人や複数のAIツールから並行して使う運用は確かめていません。一人、一プロセスで使ってください。
- 決定の改訂や取り消しのコマンドはありません。変更は、新しいIDの記録として追加します。
- 署名や時刻の証明はありません。
- MCP経由の決定の出所(クライアント名)と責任者(`responsible`)は、自己申告のままです。本人確認はありません。
- `sei add decision`をターミナルから実行した場合は、制限が働きません。`sei`のバイナリを実行できる人は、`responsible`を付けなくても決定を記録できます。既定の制限が働くのは、`sei mcp`で提供するツールだけです。
- 判断の記録(`semantic.bundle.json`)は、記録の内容としては追記のみですが、書き込みのたびにファイル全体を書き直します。そのため、`sei`が動いている間に手で編集すると、その変更は失われるおそれがあります。
- 運用のログ(`gate-checks.jsonl`)は、改ざんを検出できません。

## 9. 困ったとき

まず、次のコマンドで自己診断できます。

```bash
sei doctor --data-root /absolute/path/to/.sei
```

`sei doctor`は、バイナリの版とハッシュ、データ置き場への書き込み、記録の検証、残っているロック、ゲートログの書き込みを確かめます。読み取り専用で、記録もロックも変更しません。`fail`が一つでもあれば終了コードは1になります。`warn`は、そのままでも動く状態を表します。出力には、AIツールに登録するための絶対パスのMCP設定も含まれます。
