# SOZA 開発文書作成標準

更新日: 2026-08-31  
状態: **Accepted Documentation Standard**

## 1. 基本方針

SOZAの開発文書では、内容と構造を整えた後に、**自然な日本語となることを最重要視して全文をドラフトし直す工程**を必ず設けます。

この工程は、意味を平易化して削るためのものではありません。技術的な意味、条件、例外、留保、Evidenceの強さを保ったまま、人間が無理なく読み進められる日本語へ整えるためのものです。

## 2. 必須工程

新規作成・更新のいずれでも、開発文書は原則として次の工程を通します。

### 2.1 目的と境界を定める

文書が何を定義・判断・報告するのかを明確にします。同時に、その文書では決めないことも必要に応じて明示します。

### 2.2 事実・前提・Evidenceを確認する

未確認事項を確定事項として書きません。過去の設計資料、ローカル試験、実repository、運用実績を区別します。

### 2.3 構造を作る

読み手が、背景、論点、選択肢、判断、影響、未決事項を追える順序へ整理します。

### 2.4 技術的一貫性を確認する

Product Value、Requirements、ADR、Architecture、Contract、実装の間に矛盾がないか確認します。

### 2.5 自然な日本語へ全文をドラフトし直す

意味や仕様を変えず、日本語として自然な語順、接続、段落構成へ整えます。

特に次を確認します。

- 英単語や識別子を名詞として過剰に連結していないか。
- 「〜側」「〜系」「〜化」だけで関係を曖昧にしていないか。
- `actual`、`local`、`candidate`、`planning`等の作業メモ語を、説明なしに日本語文へ混在させていないか。
- 主語・目的語・述語の対応が読み取りやすいか。
- 箇条書きの断片だけで重要な判断理由を済ませていないか。
- 同じ概念を不用意に別名で呼んでいないか。
- 技術用語を無理に和訳した結果、逆に意味が曖昧になっていないか。

### 2.6 意味を再監査する

日本語を整えた結果、条件や留保が弱まったり、未決事項が確定事項へ変わったりしていないか確認します。

## 3. 技術用語の扱い

`Decision`、`Capability`、`Provider`、`ExactArtifactBinding`等、SOZAで識別子として意味を持つ語は無理に日本語へ置換しません。

一方、本文では必要に応じて自然な説明を添えます。

```text
悪い例:
Capability Choice production implementation start condition

改善例:
Capability Choiceのproduction実装を開始する条件
```

境界を端的に表す式は、そのまま使用できます。

```text
Recommendation != Decision != Authority != Execution
```

ただし、重要な式には本文でも自然な日本語の説明を添えます。

## 4. 現行文書と歴史資料

現行の開発文書はこの標準の対象です。

一方、次のように原文自体がEvidenceとなる資料は、自然な日本語へ直すために本文を改変しません。

- 過去Milestoneの実装報告を参照用に保存した資料
- 外部由来の原資料
- synthetic repository等、固定入力として用いるfixture
- 過去のContractをそのまま比較するためのreference copy

これらは`plan/document_review_registry.yaml`で`excluded-historical`として記録し、除外理由を残します。

## 5. 監査状態

既存文書の日本語監査状態は、次のいずれかで管理します。

- `revised` — 自然な日本語へ改稿した。
- `reviewed-no-change` — 全文を確認し、現状の日本語で意味・可読性ともに問題がないと判断した。
- `excluded-historical` — 原文保存がEvidence上必要であり、現行開発文書としての改稿対象から除外した。

`pending`は移行中にのみ使用し、`ISSUE-000015`を完了するときには残しません。
