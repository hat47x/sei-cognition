## 3. 文化的体系のprobe

文化体系は結論の根拠ではなく、空白探索のために限定使用した。

### Probe A: 「鼎」の三脚性

`鼎`という名称から、三つの支持点を一つへ潰したときに不安定になる構造がないかだけを問うた。

対象側ではすでに、次の独立性が反復して現れていた。

- semantic / realization / execution
- application / database / environment
- definition / observation / decision
- capability / provider / authority

ここから得た増分は、「三つに分類する」ことではなく、**協調する独立対象を一つのlifecycleやidentityへ畳み込んでいないかを監査する**という問いである。

この問いだけをKJへ戻し、鼎の象徴体系そのものは設計ontologyへ採用しない。

### Probe B: 生成と制御の循環

相生・相剋のような生成／制御の認知場から、設計→実行の一方向だけでなく、実行結果がどこへ戻り、どこで暴走を止めるかを問うた。

対象側ではすでに、

```text
Definition
  → Realization
  → Execution
  → Observation / Evidence
  → Reconcile / Reconsider
```

が独立資料から支持されている。

増分は、ObservationがCanonical Definitionを自動上書きしてはならず、再採用・再判断の境界を必要とするという監査点である。

これ以上体系を展開しても対象側の新しい差分が増えないため、ここで停止した。

## 7. 最終7島

### I1　業務の意味を、現在の実装より長く生かす

業務上のIntent、Task、Action、Data、Constraint、Decision等を、画面、DB、SQL、Go、workflow engineの寿命へ従属させない。

### I2　表現を一つへ統一せず、正本と派生物の関係を追跡可能にする

DSL、native SQL、Graph、Editor、generated artifactを一つへ潰さず、何がauthoritativeで何がderivedかを明示する。

### I3　協調する対象を、一つのidentityやlifecycleへ潰さない

Application / Database / Environment、Definition / Observation / Decision等、連携するからこそ独立して扱うべき対象を分離する。

### I4　実行を外部へ委ねても、命令と実状態の差を失わない

Providerへ実行を委譲しつつ、accepted、observed、completed、recoveredを区別する。

### I5　Capabilityを開き、ProviderとAuthorityを閉じ込めすぎない

人間、AI、SaaS、TEI、外部組織、custom codeを候補にできる一方、種類から信頼・権限・優先度を推定しない。

### I6　複雑な業務差異を消さず、利用時の負担だけを下げる

legacy認証、組織、Scope、既存DB、個別ルールを再現可能にしつつ、AI、標準Capability、Pattern、Editorによって通常利用を簡単にする。

### I7　SEIは「考え、選び、記憶する層」、TEIは「実行可能な業務能力へ落とす層」として接続する

SEIがTEIの実行lifecycleを飲み込まず、TEIがSEIのDecision authorityを暗黙に代行しない。Observation / Evidenceを通じて再帰的に接続する。

```text
  ├─ I2: native source / legacy schemaを保持する
  ├─ I5: auth / OSS / provider差し替えを可能にする
  ├─ I7: AI質問・Decision Memoryへ曖昧性を戻す
  └─ I1: 業務意味を簡略化のために捨てない
```

### 対立・緊張

- 一つのCanonical Modelを持つ必要 ↔ 一つの独自表現へ統一しない必要
- 厳密な意味・権限境界 ↔ 利用者が極めて楽に使えること
- Providerを交換可能にすること ↔ 現実のProvider固有差を再現すること
- AIによる自動化 ↔ Decision / Authorityを暗黙化しないこと
- 長期に残す意味 ↔ 現在必要な実装を過度に抽象化しないこと

## 9. B型文章化

この設計系列は、ローコード製品の機能数を増やす方向へ一直線に進んだのではない。むしろ、初期のX-TEA実物から得た「業務・機能・データを相互に追跡する」という強みを残しながら、旧Driverや巨大な独自定義へ意味を集中させる構造を少しずつ解体してきた。

最初に残ったのは、業務上の意味はApplication Functionや画面、Tableそのものではないという区別だった。Task / ActionとApplication Functionを分けることで、人間、AI、SaaS、物理作業、外部組織などを異なる実現手段として扱える。その区別は後に、Authoring / Canonical Semantic / Binding & Realization / Implementation & Executionという四層へ一般化された。

この一般化によって、DSLも絶対的な正本ではなくなった。TEI-native意味を記述するときは`.tei`を使えるが、SQL-authored queryではnative SQLそのものがauthoritative sourceになり得る。Graph-authoredならIRをcanonicalにできる。重要なのは表現形式を統一することではなく、何が正本で、何が派生物で、両者をどう追跡できるかを明示することである。

同じ分離はApplicationとDatabaseにも現れた。一つのApplicationが複数Databaseを使い、Application ReleaseとDatabase Releaseは別々に進む。Environmentが両者を具体ProviderへBindingする。DatabaseではDesiredとActualを比較できるが、差が見つかっただけでMigrationを自動採用しない。実行でもcommand acceptedと外部状態の変化を同一視せず、Observation / Evidenceを経て初めて完了を判断する。

Provider境界も同じ考え方で整理される。PluginはBusiness意味ではなくCapability実装の配布単位であり、Capability、Provider、Plugin package、Business IDは別のidentityを持つ。既存OSSを第一候補として利用でき、TEI自身も関連製品だからという理由だけで優先されない。

認証・認可も、簡単な標準Schemaへ現実を押し込むのではなく、標準Capability入口と差し替え可能Providerを分ける方向へ進んだ。既存システムのロック、期限、旧hash等は移行上再現できる必要がある。一方、認可はMenu表示に閉じず、APIやMCPにも通用するEntry / Resource境界として扱う。OrganizationやRoleも固定Tableへ焼き込まず、実データを意味ContractへBindingする。

AIはこの複雑性を消すためではなく、利用者が複雑性を直接背負わなくてもよくするために使う。既存Pattern、Policy、Capabilityを先に探索し、曖昧性が設計に効くときだけ質問する。質問にはStable IDを持たせ、回答を判断履歴として保存し、新しいEvidenceが衝突したら同じ質問を繰り返すのではなくImpactを示す。この部分はSEIのDecision Memoryと強く接続する可能性がある。

ここでSEIとTEIの役割が分かれる。SEIが持つべき中心は、問い、不確実性、Evidence、Recommendation、Decision、Responsibility、Capability選択等の認知・意思決定である。TEIが持つべき中心は、業務意味をApplication、Database、Provider、Deployment等へ追跡可能に実現することにある。TEIのObservation / EvidenceはSEIへ戻り、再検討を起動できる。しかし、TEIのRuntime状態をSEIのTruthへ、SEIのRecommendationをTEIのAuthorityへ自動昇格させない。

この分離を保つことが、生成AIがさらに強くなり、現在のworkflowやagent orchestrationが交換可能になっても残る設計の中心になる。
